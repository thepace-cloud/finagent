## 原理卡 #1：MySQL 隔夜断连与连接池保活（09-22 交付）

### 1. 一句话总结

「MySQL 服务端会主动掐掉闲置超过 `wait_timeout`（默认 8 小时）的连接，而应用侧的连接池不知道对面已经挂了；隔夜后第一个请求拿着一条死管道去写库，就炸出 `MySQL server has gone away`。修复两件套：**借出前先 ping**（`pool_pre_ping`）+ **连接定时退役**（`pool_recycle`）。」

### 2. 它解决什么问题

系统公网上线当天一切正常。次日早上第一个聊天请求 → 500。`docker logs` 里的真凶：

```
sqlalchemy.exc.OperationalError: (pymysql.err.OperationalError)
(2006, 'MySQL server has gone away') ... BrokenPipeError(32, 'Broken pipe')
```

出错位置是 `ensure_user()`——每个聊天请求的第一步写库操作。诡异的是**当天所有测试全绿，隔一夜就坏**。

### 3. 原理拆解：一条连接的一生

```
应用容器（app）                      MySQL 容器（mysql）
     │ ── 建立 TCP 连接 ────────────→ │
     │ ←──────── 连接建立 ──────────  │
     │      （白天测试一切正常）        │
     │                              │ ← 夜里没人提问，连接闲置
     │                              │ wait_timeout（8h）到点
     │ ←── 服务端单方面 close ──────  │ （MySQL 自我保护：清扫闲置连接）
     ✗ 应用侧连接池不知道对面已挂！
     │
   次日第一个请求：
     │ ── 从池里借出这条"死连接" ──→ 往已关闭的管道写数据
     └── BrokenPipeError → "MySQL server has gone away"
```

三个角色各司其职， bug 藏在它们的交界处：

- **TCP 连接是双向管道**：任何一端都可以单方面关闭，另一端不会收到"挂号信"通知；
- **MySQL 的 `wait_timeout`**：闲置连接占内存，服务端定期清扫——这是合理的自我保护，不是 MySQL 的错；
- **SQLAlchemy 连接池**：为了省"每次重建连接"的开销（TCP 三次握手 + 登录认证，毫秒级），用完的连接放回池里复用。但池只管借出/归还，**不负责探活**——它不知道手里那条连接已经是空壳。

**类比**：你晚上和对方通话后没挂机就睡了，对方半夜挂了。第二天你拿起听筒就开讲——只有听到忙音才知道对面早没人。`pre_ping` = 开口前先"喂？"一声；`recycle` = 这通电话最多打 1 小时，到点主动重拨，永远不给对面"半夜挂机"的机会。

### 4. 关键代码走读（v4_db.py）

```python
self.engine = create_engine(self.url, future=True,
                            pool_pre_ping=True,    # 借出前先 ping 一下
                            pool_recycle=3600)     # 连接最多活 1 小时
```

两个参数各管一半：

- **`pool_pre_ping=True`（被动自愈）**：每次从池里借连接前，先发一个轻量探测（`SELECT 1`）。活着 → 直接用；死了 → 当场丢弃、新建一条。哪怕连接被中途掐掉（MySQL 重启、网络闪断）也能自愈。
- **`pool_recycle=3600`（主动预防）**：连接年龄到 1 小时强制退役换新。3600 秒 < 8 小时的 `wait_timeout`，连接永远活不到"被掐的年纪"。

**为什么两个都要？** 只开 `recycle`：中途被掐的连接（重启、闪断）照样炸；只开 `pre_ping`：每次借出都多一次探测往返。一个管日常老化、一个管意外死亡，合起来才完整。

### 5. 设计决策与备选方案

| 方案 | 结论 |
|---|---|
| A. 调大/关闭 MySQL 的 `wait_timeout` | ✗ 治标不治本；托管数据库常不给这个权限；把清扫压力转嫁服务端 |
| B. 不用连接池，每次新建连接 | ✗ 每个请求多付毫秒级握手+认证，高并发下反而更糟 |
| C. **池参数两件套（选用）** | ✓ 应用侧自治、零外部依赖、SQLAlchemy 一行参数 |
| D. 代理层连接管理（ProxySQL 类） | 生产级正解，但对三容器 demo 是过度设计——答辩可作升级路径讲 |

### 6. 实测数字

修复部署（commit `93c5acc`）后：服务跨夜闲置，次日首请求 200 正常；09-23 重建容器后健康检查、聊天请求、双写全绿。

### 7. 答辩/面试问法与答法

**Q：「为什么本地开发从没遇到？」**
A：「本地测试会话几分钟就结束，连接永远活不到 8 小时闲置线。只有真实部署、真实过夜才暴露——这正是我们坚持公网上线而非单机演示的价值。」

**Q：「`pre_ping` 每次多一次查询，性能损失多大？」**
A：「借出时多一个 `SELECT 1` 往返，微秒级；换来的是零人工干预的自愈。性能敏感场景可以只开 `recycle` 省 ping——按流量形态取舍，我们演示场景延迟瓶颈在 LLM（秒级），ping 开销可以忽略。」

**Q：「这属于哪类问题？」**
A：「Stale connection（陈旧资源持有），分布式系统经典题。凡是『缓存了对端资源』的组件都可能踩：HTTP keep-alive 的死连接、Redis 客户端、负载均衡摘掉的后端。识别出问题类别，解法就是通用套路——探活 + 定期换新。」

### 8. 边界与取舍

只治"闲置掐线"；MySQL 整体宕机期间请求仍会失败（fail-fast 是正确行为，不是 bug）；口径是单实例——多副本部署时每个进程各自保活，互不影响。

## 原理卡 #2：/stats 运营看板页（09-23 交付）

### 1. 一句话总结

「看板页是 `/metrics` JSON 的一层皮肤——**数据只有一份**（服务进程内的计数器），页面每 5 秒拉一次、画成数字卡和占比条；页面本身不存任何数据。一个数据源，两个视图：`/metrics` 给机器，`/stats` 给人。」

### 2. 它解决什么问题

可观测性计数器（特色 3「全链路可观测」）此前只有一个出口——`/metrics` 的裸 JSON：

```json
{"counters":{"chat.total":2,"chat.rag":1,...},"timers":{"chat.seconds":{"avg":2.94,...}}}
```

工程师读得懂，**评委和演示观众读不懂**。演示时需要"数字说话"的视觉证据：问一句、数字跳一下，护栏拦截一目了然。看板页就是给这套数字开一个人人可点开的门面。

### 3. 原理拆解：一个数字的一生

```
用户提问
  → v5_app 两个 chat 端点计数：inc("chat.total")、inc("chat.rag")、inc("guard.first_pass")
  → 这些调用只是往一个带线程锁的 Python dict 里 +1，微秒级，不碰磁盘
        ↓
GET /metrics  → snapshot() 把 dict 拍照成 JSON     【视图一：给机器】
        ↓
GET /stats    → 服务器直接吐 static/stats.html     【纯静态文件，不渲染任何东西】
        ↓
浏览器：JS 每 5 秒 fetch("/metrics") → 拿到 JSON → 改 DOM
        数字卡填文本、占比条按百分比分宽               【视图二：给人】
```

三个关键认知：

- **FastAPI 里"加一个页面"的成本**：一个返回 `FileResponse("static/stats.html")` 的 GET 路由，和聊天页 `/` 同款。服务器不渲染、不计算，直接发文件（和 Nginx 发静态文件一个道理），所有渲染发生在浏览器里；
- **页面不存数据**：刷新浏览器数字不丢（数据在服务器进程里），重启服务才清零；
- **没有第二套统计逻辑**：`/metrics` 和 `/stats` 读的是同一个计数器——永远不存在"两处数字打架"，评委当场 curl `/metrics` 可以逐位核对看板上的数。

### 4. 关键代码走读（static/stats.html）

**占比条 `setBar()`**——一根 flex 容器，段是按百分比分宽的 div：

```js
d.style.width = (v / total * 100).toFixed(2) + "%";   // 占比 = 段宽
```

段与段之间留 2px 底色缝（视觉分界不靠颜色跳变）；`total=0` 时画一根灰条——空态也是态，不留白。

**主循环 `tick()`**——每 5 秒一次的"拉数-画数"：

```js
const m = await (await fetch("/metrics")).json();   // 拉
$("kTotal").textContent = total;                    // 画：数字卡
setBar("routeBar", [[rag, C.rag], [ana, C.ana]]);   // 画：占比条
```

`catch` 里显示「连接中断」——fetch 失败本身就是信号（服务挂了），页面要能自己表达这件事，而不是假装还在刷新。

**运行时长 `uptime()`**——快照里的 `started_at`（ISO 时间字符串）与当前时间做差，换算成"X 天 X 时 / X 时 X 分"。

**健康角标**——和聊天页逐字同一段 `fetch("/health")` 逻辑，两页行为一致，不各造一套。

### 5. 设计决策与备选方案

**为什么 5 秒轮询而不是 WebSocket 推送？**
轮询 = `setInterval + fetch` 三行；WebSocket = 新协议 + 连接管理 + 断线重连 + 服务端推送逻辑。演示场景 5 秒延迟人眼无感知。原则：**选够用的最简方案**（KISS）。真要秒级实时（比如股票行情页），再上 WebSocket/ SSE——本项目聊天流式已经用 SSE 了，看板不需要。

**为什么计数放进程内存，不写数据库？**
看板回答的是"这个进程活着期间干了什么"——一次评测窗口、一场演示的语义，内存计数口径刚好。MySQL 里的冷数据（谁在何时问了什么）是另一层数字，看板不掺和。重启清零写在页脚——诚实，且评委可验证。

**为什么前端不用 React/Vue？**
数据就十来个数字，单文件零构建：改一行、刷新即见，部署只是复制文件。框架解决的是"状态多了管不过来"，这里没有这个问题。

**颜色策略：颜色跟随实体。**
RAG 蓝、工具紫 = 聊天页路线徽章同款色；护栏绿/琥珀/红 = 好/警告/严重语义色（和健康角标、拒答红卡同一套）。**不新造颜色**——用户在聊天页建立的颜色认知直接复用到看板。本机没有 node 跑不了色盲校验器，按规范兜底：每个色块旁必有文字图例（名称+次数+百分比），**身份从不裸靠颜色**，色盲读者零信息损失。

### 6. 实测数字（09-23 上线当天）

| 指标 | 值 |
|---|---|
| 总请求 | 2（RAG 1 + 工具调用 1） |
| 护栏三档 | 一次通过 ×2 |
| 平均 / 最大延迟 | 2.94s / 3.37s |

演示动线：打开 `/stats` → 切聊天页问一句 → 切回看板，5 秒内总请求 +1、占比条重分宽、延迟重算——"数字说话"的镜头就这 10 秒。

### 7. 答辩/面试问法与答法

**Q：「数据存在哪？刷新页面会丢吗？」**
A：「存在服务进程内存里。刷新浏览器不丢（数据在服务器）；重启服务才清零——它度量的是本进程存活期间的行为，一次评测窗口刚好。」

**Q：「数字能造假吗？」**
A：「页面只是 `/metrics` 的视图，curl `/metrics` 当场核对，两处必须逐位一致。计数逻辑在应用代码里，随作品可审计。」

**Q：「为什么不接 Prometheus + Grafana？」**
A：「那是生产监控的标准答案，但要引入两个新组件；我们十来个指标，自研 60 行零依赖计数器口径透明、curl 可验证。升级路径是清晰的：计数器换 `prometheus_client`、页面换 Grafana 嵌入，数据语义不变——先证明需要，再上重武器。」

**Q：「多实例部署这数字还对吗？」**
A：「不对，这是单进程口径。多副本要把计数摘到进程外（Redis INCR 或 Prometheus）。我们当前是单实例，口径写清即可——知道边界比假装没有边界可信。」

### 8. 边界与取舍

不跨重启（MySQL 冷数据在，看板不展示）；无历史趋势线（只有累计值，没有时间序列——那是时序数据库的活）；单进程口径（多副本需外部聚合）。每条边界都是"知道并能说出升级路径"，而不是"没想过"。

## 原理卡 #3：多产品对比问答（09-23 验收）

> **09-29 更新**：本卡「发现的边界」一节预言的 K 固定挤占，当晚被探针实锤
>（3 例 2 翻车），且作品文档已承诺「双文档同时检索」——专门对比路径立项，
> 检测/检索/措辞全部升级，见 [原理卡 #4](#-原理卡-4多产品对比落地2026-09-29-交付)。
> 本卡保留不改：决策随证据更新的过程本身就是答辩素材。

### 1. 一句话总结

「对比类问题**不需要专门的对比模块**——混合检索天然把两份文档的相关块一起捞进上下文，模型逐条对照、双侧引用；语料没写的字段，它如实说『说明书未提及』，不编。」

### 2. 它解决什么问题

普通人选贷款最自然的问法就是「安居贷和乐享贷有什么区别」——单产品问答系统要么只答一个漏一个，要么把两个产品混成一团。对比是用户做决策的核心动作，也是评测里"检索+生成"复合能力最直观的展示。

### 3. 原理拆解：一句对比问句的一生

```
"安居贷和乐享贷的申请条件有什么区别"
   ↓ BM25 关键词检索："安居贷"精确命中 anju 块，"乐享贷"精确命中 lexiang 块
   ↓ 向量检索："申请条件"语义召回两份文档的条件段
   ↓ RRF 融合排序：两份文档的申请条件块同时进 Top-K
   ↓ 上下文 = 两份文档并列 → 模型逐条对照生成
   ↓ 双侧引用 [anju_loan P2]…[lexiang_loan P1]，出口校验照常把关
```

**为什么混合检索是关键**：纯向量会把整个问句当一团语义，容易偏向其中一份文档；BM25 保证两个产品名都精确命中——产品名这类专有名词正是 BM25 的主场。这是难点 2（混合检索）的回收利用：同一个组件，新的问题类型自动受益。

### 4. 关键代码走读

**没有新代码。** 对比能力 = 已有组件链（Router 放行 → `hybrid_search` → `build_context` → 生成+出口校验）的自然涌现。这本身就是架构的证明：**好架构对新问题类型零新代码**。若一定要"走读"，走的是 `hybrid_search` 里 BM25 与向量两份排名的 RRF 融合——两路各自排序、倒数名次相加，谁都不需要调参。

### 5. 设计决策与备选方案

**发现的边界**：K 固定时两份文档互相挤占——问「首付对比」时，安居贷的首付块会把乐享贷的块挤出 Top-K（乐享贷是纯信用消费贷，语料里**根本没有首付概念**）。

| 方案 | 结论 |
|---|---|
| 调大 K / per-doc 配额检索 | 动主链路参数，风险外溢——违背"只做加法"纪律，暂不 |
| 专门写对比分支（拆问句→分别检索→拼接） | 更可控，但加一条主链路岔路，同样违背纪律 |
| **演示走两份语料都覆盖的字段（选用）** | 申请条件/额度/期限等字段双侧齐备，对比完整 |
| embedding 针对性微调 | 根治路径（国庆 M1 起：先建 Recall@K/MRR 尺子再动手） |

「说明书未提及」不是妥协，恰是产品理念——**对比场景里诚实说"没写"比硬凑一个答案可信得多**。

### 6. 实测数字

「安居贷和乐享贷的申请条件区别」：双文档同时命中，4 个维度逐条对照，双侧引用全部落在真实页码；单侧问「乐享贷的首付」→ 如实回答说明书未提及（语料本来无此概念），带 `[lexiang_loan P1]` 引用。

### 7. 答辩/面试问法与答法

**Q：「对比是怎么实现的？有专门的对比功能吗？」**
A：「没有专门模块——BM25 保证两个产品名都精确命中，相关块一起进上下文，对照是模型读并列上下文自然完成的。这验证了架构的泛化性：新问题类型零新代码。」

**Q：「三个产品对比呢？」**
A：「同理可行，但 K 固定时挤占加剧。正解是 per-document 配额检索或 query 分解（子问题各检索再融合），已列入改进路线。」

**Q：「挤占为什么不直接调大 K？」**
A：「K 大 → 上下文变长、成本升、无关块稀释注意力。检索优化是精确手术，不是加大水龙头。embedding 微调是根治路径，先建评测尺子再动手。」

### 8. 边界与取舍

K 固定带来的挤占（已知、可复现、有改进路线）；对比广度受语料限制（三份文档）；不做子问题分解（简单问句直检索，够用）。

## 原理卡 #4：多产品对比落地（2026-09-29 交付）

> 上接 [原理卡 #3](#-原理卡-3多产品对比问答09-23-验收)：#3 预言的「K 固定挤占」
> 当晚被探针实锤，本卡是修复的完整记录。

### 1. 一句话总结

「对比从『涌现能力』升格为『专线』：**分产品子索引让每款产品在自己池子里排名**——座位从分数竞争变成结构性保证；回答先直答后对照表，没看到的字段写『未检出』而不是『说明书未提及』。」

### 2. 它解决什么问题

09-29 探针三连实锤（证据 `probe_cmp_result.json`）：

| 探针问题 | 修复前 | 病因 |
|---|---|---|
| 这几款贷款哪个年龄限制更宽松？ | ❌ 只检出安居贷，答"无法比较" | top-3 全被安居贷占位，另两款没进 context |
| 兴旺贷和安居贷的利率差别大吗？ | ❌ "资料中没有兴旺贷"（另：昨晚误写"星网贷"，是探针拼写污染） | 同上 |

护栏全程没破——模型不编造，只是诚实地说"比不了"。**这是最阴险的失效模式：系统看起来在工作，功能已经静默失效**。且作品文档承诺了"双文档同时检索、逐条对照"，必须有提交物支撑（初筛明令打击"文档所述无提交物可证明"）。

### 3. 原理拆解：对比问句的一生（新路径）

```
"这几款贷款哪个年龄限制更宽松？"
   ↓ detect_compare（确定性）：数产品名——0 个 + 比较词"哪个" + 全体指代"这几款"
   ↓ 判定 = 三款全比（anju_loan + lexiang_loan + xingwang_loan）
   ↓ 每款产品在自己子索引里跑 混合检索（BM25+向量+RRF），各取 top-3
   ↓ 合并 9 块 → 对照表提示词（先直答，再 markdown 表格逐维度对照）
   ↓ 出口校验照常：引用必须落在 9 块白名单内 → 生成器与 RAG 完全共用
```

**子索引为什么治本**：挤占的本质是"全场排名"里 A 产品的块可以挤掉 B 产品的块。分池后每款产品只和自己的块竞争——**把"希望检索公平"变成"结构性保证每款有座位"**。

### 4. 关键代码走读

- `v5_router.detect_compare()`：为什么不是 ROUTES 表一行？表能表达"命中一个词"，表达不了"数出两个**不同**产品"这种结构性条件。独立函数但同样确定性、可单测、返回值即审计记录（`anju_loan+lexiang_loan`）。三条规则保守优先：点名≥2 款 → 比；比较词+全体指代 → 三款全比；单产品+比较词 → 不算（"安居贷哪个城市能申请"是单产品题）。
- `v5_compare.build_compare_indexes()`：lifespan 里建一次，每款产品一份 `{ids, V子矩阵, BM25子索引}`。V 用 fancy indexing 切行（~7×384 float，可忽略）。**为什么不是全库检索后按产品过滤**：先发 3 张 seat 再挑 = 产品可能压根没进前 3——那正是要修的 bug。
- `v5_compare.compare_search()`：每款 `hybrid_search` 各取 k_per=3，合并排序。返回形状与 `hybrid_search` 完全一致——**下游 build_context、出口校验零改动**。
- `v5_app.py`：两个端点各加一个 `elif route_name == "compare"` 分支；流式端点把 `_rag_messages` 换成可替换的 `msgs_fn` 闭包（对比提示词换汤不换药，护栏/双写/可观测全共用）。
- 前端 `render()`：连续 `|` 开头的行 → 真 `<table>`（首行表头、丢对齐行、单元格里的引用徽章照常可点）。

### 5. 设计决策与备选方案

| 决策点 | 选择 | 备选与放弃理由 |
|---|---|---|
| k_per | 3 | 2 时"哪个年龄宽松"漏乐享贷年龄块（答案诚实但不完整）；3 实测补齐。上下文 9 块 ≈ 4500 字，DeepSeek 无压力 |
| 没查到怎么写 | **「未检出」** | 「说明书未提及」是负存在断言——基于部分 context 断言全书没写，本身就是一种编造（乐享贷 P1 明明写着 22-55 周岁）。**缺证据 ≠ 证据缺失** |
| 专门分支 vs 保持涌现 | 做专线 | #3 时按"只做加法"纪律拒绝过；09-29 两个条件变了：探针实锤失效 + 文档承诺合规压力。**纪律是护栏不是枷锁，证据变了决策跟着变** |
| 对比要不要记忆补全 | 不要 | 对比对象由 detect_compare 决定，不需要从上文借产品名；少一个变量 |

### 6. 实测数字（09-29 冒烟 + 线上探针）

- 路由自测 8/8（含 3 条对比正例 + 1 条"单产品+比较词"反例）
- 冒烟三题全绿：检测 ✓ / 每款都有座位 ✓ / 表格输出 ✓ / 引用零编造 ✓
- 线上前后对比：修复前 2/3 翻车 → 修复后 3/3 给出对照表（截图与 JSON 留档）
- **新归因弹药**：乐享贷年龄块在"年龄"查询的子榜里排倒数第一（RRF 0.0312 vs 榜首 0.0325）——查询说"年龄"、文档写"周岁"，词面全无重叠，向量也救不回。与 9 月评测的"优惠≈下浮"同病：**语义盲区，根治 = embedding 针对性微调**（国庆 M1 既定路线，此案例入证据池）

### 7. 答辩/面试问法与答法

**Q：为什么不用一个向量库按 company 过滤？**
A："先检索后过滤 = 先发 3 张座位再挑人，产品可能压根没进前 3——那正是探针确诊的 bug。子索引把排名限定在每款产品内部，座位分配从分数竞争变成结构保证。成本方面语料才 20 块，3 份小 BM25 毫秒级。"

**Q：「未检出」是什么意思？为什么不说「说明书没写」？**
A："检索没看到 ≠ 说明书没写。基于部分上下文断言全书没写，是一种无法证明的负存在断言——乐享贷 P1 写着 22-55 周岁，检索漏了就说『未提及』，评审点开原文就穿帮。『未检出』只陈述我能证明的事：本次检索没看到。"

**Q：09-23 你们说对比不需要专门模块，为什么 09-29 又做了？**
A："当时是诚实的结论——已知边界（K 固定挤占）但没实锤。09-29 探针三连两例翻车，加上文档承诺了『双文档同时检索』，证据变了决策就变。工程纪律是护栏不是枷锁：改的是一条加法分支，护栏、双写、可观测全部共用，主链路零改动。"

### 8. 边界与取舍

检测词表保守——"比一比""哪家强"等口语表述漏检时走 RAG 兜底（不误伤）；语义盲区仍在（"周岁 vs 年龄"案，等 embedding 微调）；k_per=3 使三产品对比上下文 9 块（成本可控，质量优先）；不做子问题分解（当前问句形态用不上）。
