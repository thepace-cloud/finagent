## 原理卡 #1：MySQL 隔夜断连与连接池保活（09-22 交付）

### 1. 一句话总结

「MySQL 服务端会主动掐掉闲置超过 `wait_timeout`（默认 8 小时）的连接，而应用侧的连接池不知道对面已经挂了；隔夜后第一个请求拿着一条死管道去写库，就炸出 `MySQL server has gone away`。修复两件套：**借出前先 ping**（`pool_pre_ping`）+ **连接定时退役**（`pool_recycle`）。」

### 2. 它解决什么问题

系统公网上线当天一切正常。次日早上第一个聊天请求 → 500。`docker logs` 里的真凶：

```
sqlalchemy.exc.OperationalError: (pymysql.err.OperationalError)
(2006, 'MySQL server has gone away') ... BrokenPipeError(32, 'Broken pipe')
```

出错位置是 `ensure_user()`——每个聊天请求的第一步写库操作。诡异的是**当天所有测试全绿，隔一夜就坏**。

### 3. 原理拆解：一条连接的一生

```
应用容器（app）                      MySQL 容器（mysql）
     │ ── 建立 TCP 连接 ────────────→ │
     │ ←──────── 连接建立 ──────────  │
     │      （白天测试一切正常）        │
     │                              │ ← 夜里没人提问，连接闲置
     │                              │ wait_timeout（8h）到点
     │ ←── 服务端单方面 close ──────  │ （MySQL 自我保护：清扫闲置连接）
     ✗ 应用侧连接池不知道对面已挂！
     │
   次日第一个请求：
     │ ── 从池里借出这条"死连接" ──→ 往已关闭的管道写数据
     └── BrokenPipeError → "MySQL server has gone away"
```

三个角色各司其职， bug 藏在它们的交界处：

- **TCP 连接是双向管道**：任何一端都可以单方面关闭，另一端不会收到"挂号信"通知；
- **MySQL 的 `wait_timeout`**：闲置连接占内存，服务端定期清扫——这是合理的自我保护，不是 MySQL 的错；
- **SQLAlchemy 连接池**：为了省"每次重建连接"的开销（TCP 三次握手 + 登录认证，毫秒级），用完的连接放回池里复用。但池只管借出/归还，**不负责探活**——它不知道手里那条连接已经是空壳。

**类比**：你晚上和对方通话后没挂机就睡了，对方半夜挂了。第二天你拿起听筒就开讲——只有听到忙音才知道对面早没人。`pre_ping` = 开口前先"喂？"一声；`recycle` = 这通电话最多打 1 小时，到点主动重拨，永远不给对面"半夜挂机"的机会。

### 4. 关键代码走读（v4_db.py）

```python
self.engine = create_engine(self.url, future=True,
                            pool_pre_ping=True,    # 借出前先 ping 一下
                            pool_recycle=3600)     # 连接最多活 1 小时
```

两个参数各管一半：

- **`pool_pre_ping=True`（被动自愈）**：每次从池里借连接前，先发一个轻量探测（`SELECT 1`）。活着 → 直接用；死了 → 当场丢弃、新建一条。哪怕连接被中途掐掉（MySQL 重启、网络闪断）也能自愈。
- **`pool_recycle=3600`（主动预防）**：连接年龄到 1 小时强制退役换新。3600 秒 < 8 小时的 `wait_timeout`，连接永远活不到"被掐的年纪"。

**为什么两个都要？** 只开 `recycle`：中途被掐的连接（重启、闪断）照样炸；只开 `pre_ping`：每次借出都多一次探测往返。一个管日常老化、一个管意外死亡，合起来才完整。

### 5. 设计决策与备选方案

| 方案 | 结论 |
|---|---|
| A. 调大/关闭 MySQL 的 `wait_timeout` | ✗ 治标不治本；托管数据库常不给这个权限；把清扫压力转嫁服务端 |
| B. 不用连接池，每次新建连接 | ✗ 每个请求多付毫秒级握手+认证，高并发下反而更糟 |
| C. **池参数两件套（选用）** | ✓ 应用侧自治、零外部依赖、SQLAlchemy 一行参数 |
| D. 代理层连接管理（ProxySQL 类） | 生产级正解，但对三容器 demo 是过度设计——答辩可作升级路径讲 |

### 6. 实测数字

修复部署（commit `93c5acc`）后：服务跨夜闲置，次日首请求 200 正常；09-23 重建容器后健康检查、聊天请求、双写全绿。

### 7. 答辩/面试问法与答法

**Q：「为什么本地开发从没遇到？」**
A：「本地测试会话几分钟就结束，连接永远活不到 8 小时闲置线。只有真实部署、真实过夜才暴露——这正是我们坚持公网上线而非单机演示的价值。」

**Q：「`pre_ping` 每次多一次查询，性能损失多大？」**
A：「借出时多一个 `SELECT 1` 往返，微秒级；换来的是零人工干预的自愈。性能敏感场景可以只开 `recycle` 省 ping——按流量形态取舍，我们演示场景延迟瓶颈在 LLM（秒级），ping 开销可以忽略。」

**Q：「这属于哪类问题？」**
A：「Stale connection（陈旧资源持有），分布式系统经典题。凡是『缓存了对端资源』的组件都可能踩：HTTP keep-alive 的死连接、Redis 客户端、负载均衡摘掉的后端。识别出问题类别，解法就是通用套路——探活 + 定期换新。」

### 8. 边界与取舍

只治"闲置掐线"；MySQL 整体宕机期间请求仍会失败（fail-fast 是正确行为，不是 bug）；口径是单实例——多副本部署时每个进程各自保活，互不影响。

## 原理卡 #2：/stats 运营看板页（09-23 交付）

### 1. 一句话总结

「看板页是 `/metrics` JSON 的一层皮肤——**数据只有一份**（服务进程内的计数器），页面每 5 秒拉一次、画成数字卡和占比条；页面本身不存任何数据。一个数据源，两个视图：`/metrics` 给机器，`/stats` 给人。」

### 2. 它解决什么问题

可观测性计数器（特色 3「全链路可观测」）此前只有一个出口——`/metrics` 的裸 JSON：

```json
{"counters":{"chat.total":2,"chat.rag":1,...},"timers":{"chat.seconds":{"avg":2.94,...}}}
```

工程师读得懂，**评委和演示观众读不懂**。演示时需要"数字说话"的视觉证据：问一句、数字跳一下，护栏拦截一目了然。看板页就是给这套数字开一个人人可点开的门面。

### 3. 原理拆解：一个数字的一生

```
用户提问
  → v5_app 两个 chat 端点计数：inc("chat.total")、inc("chat.rag")、inc("guard.first_pass")
  → 这些调用只是往一个带线程锁的 Python dict 里 +1，微秒级，不碰磁盘
        ↓
GET /metrics  → snapshot() 把 dict 拍照成 JSON     【视图一：给机器】
        ↓
GET /stats    → 服务器直接吐 static/stats.html     【纯静态文件，不渲染任何东西】
        ↓
浏览器：JS 每 5 秒 fetch("/metrics") → 拿到 JSON → 改 DOM
        数字卡填文本、占比条按百分比分宽               【视图二：给人】
```

三个关键认知：

- **FastAPI 里"加一个页面"的成本**：一个返回 `FileResponse("static/stats.html")` 的 GET 路由，和聊天页 `/` 同款。服务器不渲染、不计算，直接发文件（和 Nginx 发静态文件一个道理），所有渲染发生在浏览器里；
- **页面不存数据**：刷新浏览器数字不丢（数据在服务器进程里），重启服务才清零；
- **没有第二套统计逻辑**：`/metrics` 和 `/stats` 读的是同一个计数器——永远不存在"两处数字打架"，评委当场 curl `/metrics` 可以逐位核对看板上的数。

### 4. 关键代码走读（static/stats.html）

**占比条 `setBar()`**——一根 flex 容器，段是按百分比分宽的 div：

```js
d.style.width = (v / total * 100).toFixed(2) + "%";   // 占比 = 段宽
```

段与段之间留 2px 底色缝（视觉分界不靠颜色跳变）；`total=0` 时画一根灰条——空态也是态，不留白。

**主循环 `tick()`**——每 5 秒一次的"拉数-画数"：

```js
const m = await (await fetch("/metrics")).json();   // 拉
$("kTotal").textContent = total;                    // 画：数字卡
setBar("routeBar", [[rag, C.rag], [ana, C.ana]]);   // 画：占比条
```

`catch` 里显示「连接中断」——fetch 失败本身就是信号（服务挂了），页面要能自己表达这件事，而不是假装还在刷新。

**运行时长 `uptime()`**——快照里的 `started_at`（ISO 时间字符串）与当前时间做差，换算成"X 天 X 时 / X 时 X 分"。

**健康角标**——和聊天页逐字同一段 `fetch("/health")` 逻辑，两页行为一致，不各造一套。

### 5. 设计决策与备选方案

**为什么 5 秒轮询而不是 WebSocket 推送？**
轮询 = `setInterval + fetch` 三行；WebSocket = 新协议 + 连接管理 + 断线重连 + 服务端推送逻辑。演示场景 5 秒延迟人眼无感知。原则：**选够用的最简方案**（KISS）。真要秒级实时（比如股票行情页），再上 WebSocket/ SSE——本项目聊天流式已经用 SSE 了，看板不需要。

**为什么计数放进程内存，不写数据库？**
看板回答的是"这个进程活着期间干了什么"——一次评测窗口、一场演示的语义，内存计数口径刚好。MySQL 里的冷数据（谁在何时问了什么）是另一层数字，看板不掺和。重启清零写在页脚——诚实，且评委可验证。

**为什么前端不用 React/Vue？**
数据就十来个数字，单文件零构建：改一行、刷新即见，部署只是复制文件。框架解决的是"状态多了管不过来"，这里没有这个问题。

**颜色策略：颜色跟随实体。**
RAG 蓝、工具紫 = 聊天页路线徽章同款色；护栏绿/琥珀/红 = 好/警告/严重语义色（和健康角标、拒答红卡同一套）。**不新造颜色**——用户在聊天页建立的颜色认知直接复用到看板。本机没有 node 跑不了色盲校验器，按规范兜底：每个色块旁必有文字图例（名称+次数+百分比），**身份从不裸靠颜色**，色盲读者零信息损失。

### 6. 实测数字（09-23 上线当天）

| 指标 | 值 |
|---|---|
| 总请求 | 2（RAG 1 + 工具调用 1） |
| 护栏三档 | 一次通过 ×2 |
| 平均 / 最大延迟 | 2.94s / 3.37s |

演示动线：打开 `/stats` → 切聊天页问一句 → 切回看板，5 秒内总请求 +1、占比条重分宽、延迟重算——"数字说话"的镜头就这 10 秒。

### 7. 答辩/面试问法与答法

**Q：「数据存在哪？刷新页面会丢吗？」**
A：「存在服务进程内存里。刷新浏览器不丢（数据在服务器）；重启服务才清零——它度量的是本进程存活期间的行为，一次评测窗口刚好。」

**Q：「数字能造假吗？」**
A：「页面只是 `/metrics` 的视图，curl `/metrics` 当场核对，两处必须逐位一致。计数逻辑在应用代码里，随作品可审计。」

**Q：「为什么不接 Prometheus + Grafana？」**
A：「那是生产监控的标准答案，但要引入两个新组件；我们十来个指标，自研 60 行零依赖计数器口径透明、curl 可验证。升级路径是清晰的：计数器换 `prometheus_client`、页面换 Grafana 嵌入，数据语义不变——先证明需要，再上重武器。」

**Q：「多实例部署这数字还对吗？」**
A：「不对，这是单进程口径。多副本要把计数摘到进程外（Redis INCR 或 Prometheus）。我们当前是单实例，口径写清即可——知道边界比假装没有边界可信。」

### 8. 边界与取舍

不跨重启（MySQL 冷数据在，看板不展示）；无历史趋势线（只有累计值，没有时间序列——那是时序数据库的活）；单进程口径（多副本需外部聚合）。每条边界都是"知道并能说出升级路径"，而不是"没想过"。

## 原理卡 #3：多产品对比问答（09-23 验收）

> **09-29 更新**：本卡「发现的边界」一节预言的 K 固定挤占，当晚被探针实锤
>（3 例 2 翻车），且作品文档已承诺「双文档同时检索」——专门对比路径立项，
> 检测/检索/措辞全部升级，见 [原理卡 #4](#-原理卡-4多产品对比落地2026-09-29-交付)。
> 本卡保留不改：决策随证据更新的过程本身就是答辩素材。

### 1. 一句话总结

「对比类问题**不需要专门的对比模块**——混合检索天然把两份文档的相关块一起捞进上下文，模型逐条对照、双侧引用；语料没写的字段，它如实说『说明书未提及』，不编。」

### 2. 它解决什么问题

普通人选贷款最自然的问法就是「安居贷和乐享贷有什么区别」——单产品问答系统要么只答一个漏一个，要么把两个产品混成一团。对比是用户做决策的核心动作，也是评测里"检索+生成"复合能力最直观的展示。

### 3. 原理拆解：一句对比问句的一生

```
"安居贷和乐享贷的申请条件有什么区别"
   ↓ BM25 关键词检索："安居贷"精确命中 anju 块，"乐享贷"精确命中 lexiang 块
   ↓ 向量检索："申请条件"语义召回两份文档的条件段
   ↓ RRF 融合排序：两份文档的申请条件块同时进 Top-K
   ↓ 上下文 = 两份文档并列 → 模型逐条对照生成
   ↓ 双侧引用 [anju_loan P2]…[lexiang_loan P1]，出口校验照常把关
```

**为什么混合检索是关键**：纯向量会把整个问句当一团语义，容易偏向其中一份文档；BM25 保证两个产品名都精确命中——产品名这类专有名词正是 BM25 的主场。这是难点 2（混合检索）的回收利用：同一个组件，新的问题类型自动受益。

### 4. 关键代码走读

**没有新代码。** 对比能力 = 已有组件链（Router 放行 → `hybrid_search` → `build_context` → 生成+出口校验）的自然涌现。这本身就是架构的证明：**好架构对新问题类型零新代码**。若一定要"走读"，走的是 `hybrid_search` 里 BM25 与向量两份排名的 RRF 融合——两路各自排序、倒数名次相加，谁都不需要调参。

### 5. 设计决策与备选方案

**发现的边界**：K 固定时两份文档互相挤占——问「首付对比」时，安居贷的首付块会把乐享贷的块挤出 Top-K（乐享贷是纯信用消费贷，语料里**根本没有首付概念**）。

| 方案 | 结论 |
|---|---|
| 调大 K / per-doc 配额检索 | 动主链路参数，风险外溢——违背"只做加法"纪律，暂不 |
| 专门写对比分支（拆问句→分别检索→拼接） | 更可控，但加一条主链路岔路，同样违背纪律 |
| **演示走两份语料都覆盖的字段（选用）** | 申请条件/额度/期限等字段双侧齐备，对比完整 |
| embedding 针对性微调 | 根治路径（国庆 M1 起：先建 Recall@K/MRR 尺子再动手） |

「说明书未提及」不是妥协，恰是产品理念——**对比场景里诚实说"没写"比硬凑一个答案可信得多**。

### 6. 实测数字

「安居贷和乐享贷的申请条件区别」：双文档同时命中，4 个维度逐条对照，双侧引用全部落在真实页码；单侧问「乐享贷的首付」→ 如实回答说明书未提及（语料本来无此概念），带 `[lexiang_loan P1]` 引用。

### 7. 答辩/面试问法与答法

**Q：「对比是怎么实现的？有专门的对比功能吗？」**
A：「没有专门模块——BM25 保证两个产品名都精确命中，相关块一起进上下文，对照是模型读并列上下文自然完成的。这验证了架构的泛化性：新问题类型零新代码。」

**Q：「三个产品对比呢？」**
A：「同理可行，但 K 固定时挤占加剧。正解是 per-document 配额检索或 query 分解（子问题各检索再融合），已列入改进路线。」

**Q：「挤占为什么不直接调大 K？」**
A：「K 大 → 上下文变长、成本升、无关块稀释注意力。检索优化是精确手术，不是加大水龙头。embedding 微调是根治路径，先建评测尺子再动手。」

### 8. 边界与取舍

K 固定带来的挤占（已知、可复现、有改进路线）；对比广度受语料限制（三份文档）；不做子问题分解（简单问句直检索，够用）。

## 原理卡 #4：多产品对比落地（2026-09-29 交付）

> 上接 [原理卡 #3](#-原理卡-3多产品对比问答09-23-验收)：#3 预言的「K 固定挤占」
> 当晚被探针实锤，本卡是修复的完整记录。

### 1. 一句话总结

「对比从『涌现能力』升格为『专线』：**分产品子索引让每款产品在自己池子里排名**——座位从分数竞争变成结构性保证；回答先直答后对照表，没看到的字段写『未检出』而不是『说明书未提及』。」

### 2. 它解决什么问题

09-29 探针三连实锤（证据 `probe_cmp_result.json`）：

| 探针问题 | 修复前 | 病因 |
|---|---|---|
| 这几款贷款哪个年龄限制更宽松？ | ❌ 只检出安居贷，答"无法比较" | top-3 全被安居贷占位，另两款没进 context |
| 兴旺贷和安居贷的利率差别大吗？ | ❌ "资料中没有兴旺贷"（另：昨晚误写"星网贷"，是探针拼写污染） | 同上 |

护栏全程没破——模型不编造，只是诚实地说"比不了"。**这是最阴险的失效模式：系统看起来在工作，功能已经静默失效**。且作品文档承诺了"双文档同时检索、逐条对照"，必须有提交物支撑（初筛明令打击"文档所述无提交物可证明"）。

### 3. 原理拆解：对比问句的一生（新路径）

```
"这几款贷款哪个年龄限制更宽松？"
   ↓ detect_compare（确定性）：数产品名——0 个 + 比较词"哪个" + 全体指代"这几款"
   ↓ 判定 = 三款全比（anju_loan + lexiang_loan + xingwang_loan）
   ↓ 每款产品在自己子索引里跑 混合检索（BM25+向量+RRF），各取 top-3
   ↓ 合并 9 块 → 对照表提示词（先直答，再 markdown 表格逐维度对照）
   ↓ 出口校验照常：引用必须落在 9 块白名单内 → 生成器与 RAG 完全共用
```

**子索引为什么治本**：挤占的本质是"全场排名"里 A 产品的块可以挤掉 B 产品的块。分池后每款产品只和自己的块竞争——**把"希望检索公平"变成"结构性保证每款有座位"**。

### 4. 关键代码走读

- `v5_router.detect_compare()`：为什么不是 ROUTES 表一行？表能表达"命中一个词"，表达不了"数出两个**不同**产品"这种结构性条件。独立函数但同样确定性、可单测、返回值即审计记录（`anju_loan+lexiang_loan`）。三条规则保守优先：点名≥2 款 → 比；比较词+全体指代 → 三款全比；单产品+比较词 → 不算（"安居贷哪个城市能申请"是单产品题）。
- `v5_compare.build_compare_indexes()`：lifespan 里建一次，每款产品一份 `{ids, V子矩阵, BM25子索引}`。V 用 fancy indexing 切行（~7×384 float，可忽略）。**为什么不是全库检索后按产品过滤**：先发 3 张 seat 再挑 = 产品可能压根没进前 3——那正是要修的 bug。
- `v5_compare.compare_search()`：每款 `hybrid_search` 各取 k_per=3，合并排序。返回形状与 `hybrid_search` 完全一致——**下游 build_context、出口校验零改动**。
- `v5_app.py`：两个端点各加一个 `elif route_name == "compare"` 分支；流式端点把 `_rag_messages` 换成可替换的 `msgs_fn` 闭包（对比提示词换汤不换药，护栏/双写/可观测全共用）。
- 前端 `render()`：连续 `|` 开头的行 → 真 `<table>`（首行表头、丢对齐行、单元格里的引用徽章照常可点）。

### 5. 设计决策与备选方案

| 决策点 | 选择 | 备选与放弃理由 |
|---|---|---|
| k_per | 3 | 2 时"哪个年龄宽松"漏乐享贷年龄块（答案诚实但不完整）；3 实测补齐。上下文 9 块 ≈ 4500 字，DeepSeek 无压力 |
| 没查到怎么写 | **「未检出」** | 「说明书未提及」是负存在断言——基于部分 context 断言全书没写，本身就是一种编造（乐享贷 P1 明明写着 22-55 周岁）。**缺证据 ≠ 证据缺失** |
| 专门分支 vs 保持涌现 | 做专线 | #3 时按"只做加法"纪律拒绝过；09-29 两个条件变了：探针实锤失效 + 文档承诺合规压力。**纪律是护栏不是枷锁，证据变了决策跟着变** |
| 对比要不要记忆补全 | 不要 | 对比对象由 detect_compare 决定，不需要从上文借产品名；少一个变量 |

### 6. 实测数字（09-29 冒烟 + 线上探针）

- 路由自测 8/8（含 3 条对比正例 + 1 条"单产品+比较词"反例）
- 冒烟三题全绿：检测 ✓ / 每款都有座位 ✓ / 表格输出 ✓ / 引用零编造 ✓
- 线上前后对比：修复前 2/3 翻车 → 修复后 3/3 给出对照表（截图与 JSON 留档）
- **新归因弹药**：乐享贷年龄块在"年龄"查询的子榜里排倒数第一（RRF 0.0312 vs 榜首 0.0325）——查询说"年龄"、文档写"周岁"，词面全无重叠，向量也救不回。与 9 月评测的"优惠≈下浮"同病：**语义盲区，根治 = embedding 针对性微调**（国庆 M1 既定路线，此案例入证据池）

### 7. 答辩/面试问法与答法

**Q：为什么不用一个向量库按 company 过滤？**
A："先检索后过滤 = 先发 3 张座位再挑人，产品可能压根没进前 3——那正是探针确诊的 bug。子索引把排名限定在每款产品内部，座位分配从分数竞争变成结构保证。成本方面语料才 20 块，3 份小 BM25 毫秒级。"

**Q：「未检出」是什么意思？为什么不说「说明书没写」？**
A："检索没看到 ≠ 说明书没写。基于部分上下文断言全书没写，是一种无法证明的负存在断言——乐享贷 P1 写着 22-55 周岁，检索漏了就说『未提及』，评审点开原文就穿帮。『未检出』只陈述我能证明的事：本次检索没看到。"

**Q：09-23 你们说对比不需要专门模块，为什么 09-29 又做了？**
A："当时是诚实的结论——已知边界（K 固定挤占）但没实锤。09-29 探针三连两例翻车，加上文档承诺了『双文档同时检索』，证据变了决策就变。工程纪律是护栏不是枷锁：改的是一条加法分支，护栏、双写、可观测全部共用，主链路零改动。"

### 8. 边界与取舍

检测词表保守——"比一比""哪家强"等口语表述漏检时走 RAG 兜底（不误伤）；语义盲区仍在（"周岁 vs 年龄"案，等 embedding 微调）；k_per=3 使三产品对比上下文 9 块（成本可控，质量优先）；不做子问题分解（当前问句形态用不上）。

## 原理卡 #5：贷款适配测评——确定性打分路径（2026-09-30 交付）

> 系统里唯一**完全不走大模型**的路径。上接作品主张「数字交给代码算」：
> 这次把整个功能都交给代码算。

### 1. 一句话总结

「测评 = 问卷答案 × 说明书条款的**查表推论**：硬门槛（用途/客群/年龄/期限/金额，每条挂页码）先定资格，软评分再排座次，规则代码毫秒出推荐卡——连月供都用说明书 P3 的公式现场算，手册自带示例就是单元测试。」

### 2. 它解决什么问题

初筛五进一，需要"AI 明显 + 创意 + 演示高潮"的功能；用户真实痛点不是"问规则"而是"**我该选哪款**"——决策问题。让 LLM 做测评推荐 = 把可验证的规则变成不可复现的口算：同一个人两次测评可能得到不同推荐，金融场景不可接受。对照：主链路的出口校验本质也是压缩 LLM 自由度——测评只是把这个哲学推到底，**语义该管的归 LLM（理解问句、读原文），查表和算术归代码**。

### 3. 原理拆解：一份问卷的一生

```
用户点「📋 适配测评」
   ↓ GET /assess 拉题（问卷与打分规则同源，单一事实源）
   ↓ 5 道选择题点选（经营用途才追加条件题，show_if 控制）
   ↓ POST /assess {answers}
   ↓ 硬门槛五连查：用途 → 客群(经营满2年) → 年龄 → 期限 → 金额
     （不过 = 出局，逐条挂说明书引用；三款全被拦 → 诚实全拒卡）
   ↓ 软评分：40 底 + 用途20/年龄15/期限15/金额10/特色5，封顶100
   ↓ 推荐卡：首选（匹配度条+理由+顾虑）+ 逐款说明 + 月供估算
   ↓ 出口引用校验：每条 cite 必须真实存在于语料——失锚当场 500 暴露
```

**宁拒不错在测评路径的形态**：56 岁想消费贷（乐享超龄、其余用途不符）→ 不硬推"最不差的"，直接"三款均不适合"+ 逐款原因 + 转人工建议。

### 4. 关键代码走读

- `v5_assess.QUESTIONS`：选项 `value` 直接是打分规则的输入键，前端不硬编码——改问卷不用两头对表。条件题（经营满 2 年）只在 `purpose=business` 时出现。
- `_band_fail()` 区间语义：冒烟抓过 bug——「未满 18」是开区间 band `(None,17)`，只查 band 下界会漏判，开区间必须看上界是否低于门槛；越上限判 `lo >= g_hi`（需求区间从上限起步 = 硬失败），从上限之下骑线跨过的（300 万以上 vs 安居 500 万上限）不拦、走顾虑披露。**金融场景宁可拦错推荐，不放行超额期望**。
- `monthly_payment()`：公式逐字取自各说明书 P3「6.1 等额本息还款法」。三份手册各带一个算好的示例——**手册即黄金测试向量**（100万/4.75%/360期→5,216 元，逐元命中）。
- 出口引用校验（`v5_app.py` POST /assess）：规则表也是"生成物"，挂错页码与 LLM 编造引用同罪——运行时强制 (doc,page) 真实存在，失锚 500 暴露不静默。**把「文档-代码一致性」变成运行时断言**。

### 5. 设计决策与备选方案

| 决策点 | 选择 | 备选与放弃理由 |
|---|---|---|
| 问卷问什么 | 用途/条件题/年龄/期限/金额 | 原计划含「月收入」——三份说明书都只写"稳定收入来源"无数字门槛，问收入要么摆设要么逼编造；换成金额，三家有真实上下限。**只问语料撑得住的问题** |
| 全选择题 | 是 | 答案 value 即规则输入键，零解析歧义 |
| 权重 | 用途 20 最重 | 三款用途正交，用途即定档；年龄/期限/金额是资格维度；硬门槛不过直接出局不参与打分，避免"超额消费需求被评分美化成可选" |
| 月供估算 | 说明书公式现场算 | LLM 口算月供 = 重演"数字交给代码算"要防的事；期限选"还没想好"就明说算不了，不硬凑 |
| 进不进 route() | 不进 | 测评是多步主动流程，不是一句话的分类问题；入口在前端，不抢 /chat 关键词地盘（只做加法纪律） |
| 测评写不写记忆/双写 | 不写 | 工具端点不是对话轮次，不污染会话记忆 |

### 6. 实测数字

- 公式校准 3/3 精确命中手册示例（5,216 / 3,074 / 14,851 元）
- 冒烟 6 画像全绿（含 3 条诚实全拒：56 岁消费 / 经营不满 2 年 / 消费要 20 万+）
- 本地探针 5/5、线上探针 5/5（证据 `probe_m2_result.json`）；RAG 主链路回归通过
- 月供自洽：200万/30年/4.75% → ¥10,433 = 手册 100 万示例 ×2
- 出卡耗时：服务端毫秒级（无 LLM 调用），探针全组 2.9s（含 1 次 RAG 回归的 LLM 调用）

### 7. 答辩/面试问法与答法

**Q：测评为什么不用大模型？你们不是 AI 作品吗？**
A："AI 用在语义该管的地方——理解问句、读检索原文；查表判定和算术归代码。测评每条结论都是『说明书条款 × 用户答案』的确定性推论，LLM 口算会把可验证规则变成不可复现输出——同一人两次测评推荐不同，这在金融场景不可接受。RAG 路径的出口校验也是在压缩 LLM 自由度，同一个工程哲学。"

**Q：打分权重怎么定的？**
A："权重只管呈现排序，资格线在硬门槛——门槛不过直接出局，绝不参与打分，防止『明显不合适』被评分美化。权重序：用途 20（三款用途正交，用途即定档）> 年龄/期限 15 > 金额 10 > 特色 5。诚实说：权重是设计值不是市场验证值，但正因为如此卡片才必须每条挂出处——评审可以逐条质疑，每个数字有页码可查。"

**Q：三款全不适合，用户白答了？**
A："不白答——诚实全拒卡逐款说明被哪条条款拦下（挂引用），并建议转人工。这比硬推一款最不差的更可信：金融产品的『勉强合适』就是最差选择。"

**Q：说明书改版了，规则表怎么跟着走？**
A："规则表每条挂页码，运行时出口校验强制 (doc,page) 真实存在——说明书改版导致页码漂移，下一次请求当场 500 暴露，不会静默给错出处。这是把文档-代码一致性变成运行时断言，冒烟测试再用手册示例校准公式，双保险。"

### 8. 边界与取舍

打分权重为设计值（呈现用，资格线在硬门槛）；月供取区间中值 + 普通档基准利率，是估算口径非报价（卡片明示"实际以银行审批为准"）；条件题只覆盖兴旺贷经营年限，安居贷"已签购房合同"作顾虑披露而非门槛（答不上来不该直接出局）；规则表锚定当前三份说明书——扩产品 = 扩规则表 + 扩引用，出口校验兜底。

## 原理卡 #6：记忆可视化——画像可编辑且行为可见变化（2026-09-30 交付）

### 1. 一句话

画像不是存在 Redis 里给人看的摆设——它被检索链路真实消费：面板上改一个字，下一轮回答变一个数。

### 2. 为什么需要这张卡

V4 建了三 key 记忆（`chat_history:{session}` LIST / `summary:{user}` STRING / `profile:{user}` HASH），
但 profile 从建成那天起**没有任何链路读它**——写了不读等于没有。M3 补上消费端：
检索补全的兜底级 + 套型定向，再配一个可编辑面板让"它记得我"肉眼可见。
这也是打分逻辑里的"AI 功能明显"：记忆不是日志，是输入。

### 3. 三级补全的优先序（为什么是这个序）

```
用户问句 ──点名产品？──是──> 直接用本轮（最准）
              │否
              ├──近 6 轮 + 摘要里出现过？──> 借上文（次准，近因优先）
              │否
              └──画像 product 有意向产品？──> 画像兜底（跨会话长记忆）
```

- **本轮 > 近因 > 画像**：信息越新鲜越可信，画像是最老的信息，只配兜底。
- 兜底命中即冷启动成功：新会话第一句"申请条件是什么"（不点名）也能答乐享贷，
  因为上一场会话里用户说过意向——这就是"跨会话记忆"和"会话上下文"的区别。
- C++ 类比：三级像是 `if/else if/else` 的短路链——前面命中后面不再求值，
  避免老画像覆盖新意图。

### 4. 套型定向：为什么单独 if 而不并进三级

```python
if (profile.get("housing") in ("首套", "二套")
        and "安居贷" in q
        and any(k in q for k in ("利率", "利息", "月供", "费率"))):
    q += f" {profile['housing']}住房"    # 语料措辞「首套住房」，BM25 命中更稳
```

- 安居贷利率在 P2 按**首套 3.95 / 二套 4.45** 分行——不拼套型，检索大概率落到首套行，
  二套用户得到错答案且**错得很有信心**（引用都是真的）。
- 拼词用「首套住房」不是「首套」：对齐语料原文措辞，BM25 关键词命中更稳——
  这是混合检索的已知偏好（#4 卡同款经验）。
- 只对利率类词触发：问"申请条件"时拼套型是噪音。

### 5. 面板 = 真数据 + 白名单写

- GET `/profile`：画像 + 本会话快照（消息数 / 提过的产品）。快照只读不写。
- POST `/profile`：**白名单校验**（housing ∈ {未设置,首套,二套}，product ∈ 四值），
  budget 自由文本但限长 20。
- 为什么白名单而不是任意字段：画像会被拼进检索 query——任意文本进补全
  等于把 prompt 注入面开进检索入口。值域可枚举，注入无从谈起。
  （对照 #5 卡的出口引用断言：一个管"写进来的东西"，一个管"说出去的引用"。）

### 6. 主链路安全性（只做加法的验证方式）

`_query_with_memory` 是主链路里唯一被 M3 改动的函数。等价性护栏：
**画像为空时，三级退化成原逻辑**（本轮 → 上文，没有画像分支），行为与 V4 完全一致。
探针第 6 连用**空画像用户**跑 RAG 回归（`m3_plain` 问兴旺贷）——就是验证这个退化。

### 7. 实测

本地探针 6/6、线上探针 6/6（证据 `probe_m3_result.json`）：

| 探针 | 断言 |
|---|---|
| 画像存取 | POST 后 GET 回读一致；"三套"被白名单 400 拦下 |
| 行为 A | 画像=二套，问"安居贷的利率是多少" → 答案含 4.45 + [anju_loan P2] |
| 行为 A' | 面板改成首套，同一句再问 → 3.95 + [anju_loan P2]（行为可见变化） |
| 行为 B | 新会话不点名问"申请条件是什么" → 乐享贷兜底命中 |
| 会话快照 | 消息数、提过产品与真实会话一致（含简称去重：安居 ⊂ 安居贷 只留全称） |
| 回归 | compare 路由不伤；空画像用户 RAG 行为不变 |

### 8. 答辩问法与答法

**Q：改个画像就变答案，这跟"记住用户"有什么关系？不就是关键词替换？**
A："关键词替换正是记忆的最小可信实现。重点不在替换这个动作，而在三件事：①画像存在 Redis 跨会话持久，换个会话依然生效（冷启动兜底可现场演示）；②它只是检索 query 的一部分，答案仍走检索+生成+出口校验全链路——记忆影响召回，不越过护栏；③兜底优先序保证新意图永远压过老画像。高级做法（把画像拼进 system prompt）反而绕过了检索白名单，得不偿失。"

**Q：画像会不会被用来画用户/泄隐私？**
A："画像字段只有三个且全是白名单枚举（套型/意向产品/预算区间），没有身份信息；会话快照只统计数量和产品名，不导出原文。演示时用完可在面板一键清空（设回未设置）。"

**Q：为什么 budget 不接进行为，不是白做了？**
A："接线就要让自由文本进检索 query——那是注入面。budget 定位是面板展示的上下文提示（提醒用户自己填过什么），行为接线留给决赛：做成枚举区间（10万以下/10-30万/30万以上）再进测评路径的金额题预填。"

### 9. 边界

画像只影响检索 query（召回侧），不进生成 prompt、不改变路由判定；摘要（summary key）本期未消费，留决赛做"长期记忆压缩"；多用户画像隔离靠 user_id，本期无鉴权（演示场景单人使用，公网多用户需加会话鉴权——已记入展望）。

## 原理卡 #7：会话回放与 IP 限流——演示服务的两块补板（2026-10-02 交付）

### 1. 一句话

记忆闭环的最后一块（服务端记得 → 用户看得见：刷新不丢对话）＋公网裸奔服务的防烧钱闸门（扫描器已经在敲门）。

### 2. 会话回放：为什么"记得"要看得见

M3 之后记忆全在服务端（Redis LIST/画像 HASH），但页面一刷新前端就"失忆"——
用户感知不到它记得。补两件：

- 后端 `GET /history?user_id&session_id`：纯只读 `lrange` 时序还回消息。
  不写、不计数、不调 LLM；limit 封顶 100。
- 前端：session id 存 localStorage（刷新回同一会话），「🆕 新对话」才轮换；
  轮换的是会话，**画像不动**——短记忆（会话级）与长记忆（跨会话）的
  分界线又演示了一遍。

设计细节：欢迎页 HTML 先"拍照存底"（`WELCOME_HTML`），新对话时原样还原；
历史恢复复用 `render()`——引用徽章照常可点（事件委托的好处）。

### 3. IP 限流：为什么是现在、为什么是滑动窗口

访问日志实锤：34.x / 66.x / 199.x 云厂商段已在敲门。服务公网 IP 直连、
无登录，`/chat` 每次调用烧真钱——被脚本扫到刷接口 = 烧钱事故。

- **两档**：对话 20 次/min/IP（贵的管紧），测评/画像 60 次/min（零 LLM
  只防洪水）。GET 全放开（/metrics 每 5 秒自轮询，限了看板就坏）。
- **滑动窗口 vs 固定窗口**：固定窗口在边界会放过 2×limit 突发（前窗尾 +
  后窗头）；滑动窗口看"过去 60s 内时间戳个数"，无边界漏洞。代价是每 IP
  存时间戳列表——演示规模可忽略。
- **进程内存不是 Redis**：与 /metrics 同一哲学——度量本进程存活期间的
  行为，重启清零可接受；多实例部署才需要共享计数（留决赛）。
- 429 带 `Retry-After: 10`；流式前端加了 `!r.ok` 防护（SSE 没开流时读
  错误 JSON，气泡不会卡在"思考中"）。

### 4. 途中抓的 bug（探针的哲学）

首跑 65 发全过、零掐流——**/profile 漏挂限流**（我只挂了 /assess）。
探针的巧思：用非法体打（housing="spam"）——过闸的得 400（校验拦下，
profile.update 计数器零污染），超闸的 429；**400/429 的分界就是闸门位置**，
一个探针同时验证了限流和白名单两层。

### 5. 实测

本地 5/5、线上 5/5（证据 `probe_m35_result.json`）：历史回放两句→四条时序
正确、空会话不炸、65 发正好 60 过 5 掐、风暴后正常对话 200（chat 与 light
独立桶）、SSE 流式回归通过。Edge 无头真渲染验证前端脚本无致命错。

### 6. 答辩问法与答法

**Q：限流会不会误伤评委连续提问？**
A："人类节奏打不到 20 次/分钟——一次回答要 2-5 秒还要阅读。阈值按'正常
演示最大密度 × 安全余量'定的；造流量的脚本也做了 1.5 秒配速自证不会误伤。"

**Q：会话恢复和"新对话"按钮，画像会丢吗？**
A："不会。轮换的只是 session id——会话记忆（LIST）归零，画像（HASH）不动。
这正好是两级记忆的分界：会话级短记忆随新对话清空，跨会话画像一直都在。"

**Q：为什么限流不放在 nginx/网关层？**
A："当前架构没有网关层（IP 直连 + docker compose），加一层 nginx 只为限流
是过度设计。应用层滑动窗口十行代码解决真问题；真要多实例扩容，把计数
搬去 Redis 是半小时的事——接口不变，实现可换。"

### 7. 边界

共享 demo_user 的多访客隔离靠各自浏览器的 session id（同浏览器才共享
会话历史）；限流按 IP——同一出口 NAT 多人共享时会互相挤占（演示场景
可接受）；历史恢复不还原路线徽章与红卡样式（存储里只有文本，如实呈现）。

## 原理卡 #8：查询同义扩展——被评测闸门拦下的上线（2026-10-02，负结果）

### 1. 一句话总结

假设「红题是查询词与文档词零重叠的语义盲区」→ 上线前评测闸门全量重跑
持平（13/16）→ 控制实验证明真实问法行为零增益 → **回滚接线，负结果留档**。

### 2. 解决什么问题（本来想解决什么）

09-29/10-01 两轮评测稳定复现三个红题，当时归因到词面：
g15 问"年龄"、文档写「18 周岁至 60 周岁」；g05 问"优惠"、anju 写「下浮」。
设想在检索调用处把同义词拼进查询（`年龄→周岁`、`优惠→下浮`），生成
prompt 不动——扩展只影响召回不影响表述。

### 3. 闸门与证据链（这张卡的核心）

1. **词条纪律**：`v5_qexpand.py` 只收有红题证据的词条，每条能指出修的
   是哪一题——不拍脑袋堆同义词典。
2. **评测闸门**：`v3_eval.py` 加第三模式 `hybrid+expand` 全量重跑。
   结果：13/16 与 hybrid 完全持平，g05/g15 没翻绿也没翻红。
3. **控制实验**（证伪的关键一步）：把线上探针用的真实问法分别过
   plain/expand 的 hybrid_search 看 top-3——
   - 「安居贷的利率有优惠吗？」两种模式 top-3 **完全一致**（anju_loan_1
     本来就排第 2）——探针通过是检索本来就行，与扩展无关；
   - 「兴旺贷对借款人的年龄有什么要求？」两种模式 top-3 也一致，且都
     **不含年龄块**——探针里 `[xingwang_loan` 前缀匹配过的是 _3/_4 块。
4. **归因修正**：xingwang_loan_0 原文是「借款人**年龄**在 18 **周岁**至
   60 周岁之间」——「年龄」词面本来就有重叠，**初始归因就是错的**。真实
   根因是查询稀释：三产品比较句的大词量把年龄/周岁两个 bigram 摊薄（与
   g03 同病）。线上真实对比问法走 `detect_compare` → 分产品子索引，根本
   不经过这条单索引路径。
5. **处置**：线上接线回滚（v5_app.py 留墓碑注释）；模块与评测第三模式
   保留——每次跑评测都会自动复述这个假设被证伪的过程。

### 4. 为什么这比"上线一个没坏处的层"好

评测持平 + 行为零增益 = 这个层**没有可测量的收益**。上线前两天 ship 一个
no-op 层，增加的是审查面和"它到底干了什么"的答辩风险，换来的是零证据的
功能叙事。反过来，"我们提出假设→建闸门→假设被证伪→回滚→根因修正为
查询稀释→正确解法（分产品子索引）已在线上 compare 路径实现"是完整的
工程判断链——负结果也是结果，关键是它有证据。

### 5. 答辩问法与答法

**Q：你们检索还有什么没解决的？**
A："三个红题的根因都归因到了查询稀释——多产品比较句在单索引里词量摊薄。
生成环境的解法是 compare 路由配分产品子索引，结构性保证双侧覆盖；评测
量的是单索引路径，所以这几个题在评测里是红的、在产品里不是。我们试过
同义扩展这条路，评测闸门加控制实验证伪后回滚了，模块留档。"

**Q：怎么判断一个优化该不该上线？**
A："先定闸门再动手：我们的规矩是全量评测翻红即回滚、翻绿才留。这次
扩展是持平——持平且控制实验无行为增益，就当 no-op 回滚。上线的东西
必须能指着数字说出它买到了什么。"

### 6. 边界

「优惠→下浮」在无产品锚词的评测句（g05）上确实把 golden 块从 top-6 外
拉到第 5——方向对但幅度不够（golden 要求两块同时进 top-3）；这条留着
当未来 K 值/分块策略调整时的参考证据，不当上线依据。

## 原理卡 #9：滚动摘要接线——V4 建而未用的第三层终于上线（2026-10-02 交付）

### 1. 一句话总结

V4 设计了三层记忆（原始对话/画像/摘要），但服务端从未调用
`maybe_roll_summary`——summary key 永远是空的。M4b 把它接上：历史到
8 条自动把最旧 4 条压成摘要再裁掉，长对话的"记得住"不再无限膨胀。

### 2. 原理拆解

```
每轮对话后：history_len ≥ 2×keep(8)？
  ├─ 否 → 什么都不做（零成本）
  └─ 是 → LLM 把最旧 4 条压成 2-3 句要点
          → 拼进 summary:{user_id}（滚动累加）
          → ltrim 裁掉已被压缩的 4 条
```

摘要只在跨越阈值时算一次，不是每轮重算——省钱，也是"增量更新"的增量。
key 按 **user** 而不是 session 划分（V4 的原始设计意图）：摘要=被压缩的
远期，跨会话保留——「新对话」后画像和摘要都还在，只有会话原始历史归零，
正好是三级记忆的现场教材。

### 3. 代码走读

- 接线点：/chat 与 /chat/stream 双写（Redis+MySQL）之后，`try:
  maybe_roll_summary(memory, chat_safe) except: logger.warning`——
  **压缩失败不许连累已生成的回答**，降级为 warning（摘要丢了下轮还能
  再压，回答丢了用户白等半天）。
- `chat_safe` 是带重试的 LLM 通道（与生成共用护栏基建），不是裸调用。
- 生成侧消费：`memory_context()` 把【用户画像】【更早对话摘要】【最近
  对话】三段拼进 system——空段自动不出现，所以没摘要时行为与 V4 完全
  一致（加法纪律：新机制不改变无摘要用户的行为）。

### 4. 实测

探针 p2（`v5_m4b_probe.py`）：同会话连聊 5 轮 → `GET /history` 返回
total=6 而非 10——第 4 轮末（8 条）触发压缩裁剪，剩余窗口
[q3,a3,q4,a4,q5,a5]，新最旧条正是第 3 问。total 的收缩就是滚动发生的
行为学证据，不需要翻 Redis。

### 5. 答辩问法与答法

**Q：为什么不直接把历史全塞给模型？**
A："上下文窗口是租来的，按 token 计费。全量历史线性膨胀成本和延迟；
滚动摘要把远期压成常数大小的要点，近窗口保真、远期保梗概——'能记住的'
不随对话变长而无限膨胀。"

**Q：摘要会不会越滚越长？**
A："会——STRING 滚动累加是当前实现的已知边界，演示生命周期内无感。
真要收敛可以做'摘要的摘要'二级压缩或截断最旧段，接口不用动。"

**Q：压缩用的 LLM 调用失败了怎么办？**
A："try/except 降级：这轮不压，回答照常返回，日志留 warning。下一轮
历史更长仍然会再次触发——自愈，不需要人工干预。"

### 6. 边界

摘要质量依赖 LLM，可能丢细节（所以近 4 条永远保真不压缩）；流式端点的
滚动发生在 done 事件前的生成器里，探针只覆盖了 /chat 路径的滚动验证
（两处代码同款）。
